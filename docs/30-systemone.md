# 30 - Native Microsoft Decision / Systemone / Luna / Image

Raven exposes `POST /v1/systemone` plus the Copilot-native `POST /v1/decisions`
and `POST /v1/images/generations` JSON endpoints, plus native multipart
`POST /v1/images/edits`. They are not Chat Completions or protocol translation
paths. No model name or response field is synthesized.

## Verified Live Binding

On 2026-10-28, an explicitly authorized diagnostic reused the GitHub credential
of the existing Raven process on port 7024. One token exchange succeeded; its
`endpoints.api` was `https://api.enterprise.githubcopilot.com`. Exactly one model
request was sent to that host's `/v1/systemone`, with no redirect following,
retry, alternate path, or model fallback. It returned HTTP 200 in 1680 ms.

Request:

```json
{
  "model": "microsoft-decision-1",
  "state": "A small code change has not been tested.",
  "questions": {
    "next_step": {
      "type": "choice",
      "instructions": "Choose the next step.",
      "criteria": {
        "test": "Run the focused tests.",
        "merge": "Merge without testing."
      }
    }
  }
}
```

Observed response, not a synthetic probability fixture:

```json
{
  "model": "microsoft-decision-1",
  "answers": {
    "next_step": {
      "choice": "test",
      "confidence": 0.9976609791233872,
      "probabilities": {
        "merge": 0.001169510438306388,
        "test": 0.9988304895616936
      },
      "type": "choice"
    }
  },
  "usage": { "input_tokens": 45, "output_tokens": 1 }
}
```

The direct diagnostic proves this credential's access to this model/path at
that time, not every plan's entitlement, every question type, or the new Raven
route. Private evidence is outside Git in
`/private/tmp/raven-decision-live.KZhSJX/report.json` and `response.txt`.
No credential was printed or persisted in those artifacts. The existing 7024
process and its checkout were not modified or restarted.

## Copilot Luna Decisions and Flare Image Generations

`gpt-6-luna-decisions` is eligible only when the Copilot catalog declares the
exact `/v1/decisions` endpoint. Raven forwards a non-streaming native JSON body
with `model`, `input`, a nonempty `questions` array and unknown fields intact.
It does not translate this model to Systemone or Chat Completions.

`gpt-image-2.5-flare` is eligible only when the Copilot catalog declares the
exact `/v1/images/generations` endpoint. Raven forwards the native JSON body,
including `prompt` and unknown fields, and preserves the upstream response text.
Success image data, including `b64_json`, is response transport only and is not
written into request logs.

These routes use the Copilot token's validated API destination, manual redirect
handling, unified API-key admission, key routing, IP admission, quota and
request logs. Environment/database keys are accepted by the existing AI route
middleware; internal credentials and custom-provider rules remain excluded.
The Luna/Flare routes may observe only reported protocol usage; missing or
invalid buckets stay unobserved rather than being fabricated.

All native JSON payload fields remain data, including unknown fields and
`upstream_id`. Routing never reads `upstream_id` or another payload field:
the authenticated key's rule and server-owned Copilot destination remain
authoritative. Model fields still resolve through the key's selected rule,
but unknown payload fields are preserved upstream without routing control.
No inference retry, credential refresh, redirect follow or account fallback is
allowed. HTTP and HTTP-200 semantic errors preserve their native JSON and status,
with credential-bearing text redacted and bounded.

### Flare Image Edits: Transport Support, Not Live Acceptance

Raven v3.3.0 implemented only the generations JSON path. The maintainer explicitly
described multipart edits as unimplemented and unverified in
[#502](https://github.com/nocoo/raven/issues/502#issuecomment-6682586780);
there was no documented upstream prohibition.

`POST /v1/images/edits` now accepts `multipart/form-data` with one nonempty
`model`, one nonempty `prompt`, and uploaded `image` or `image[]` files.
Multiple images, an optional `mask`, filenames, media types, binary contents,
repeated fields and unknown fields are preserved. Optional model-specific
parameters and image/mask constraints remain upstream validation, not a Raven
allowlist. `stream` must be omitted or `false`; Raven does not support partial
image SSE. JSON/URL/file-ID image inputs and image variations are not implemented
by this multipart route.

The selected model must declare exactly `/v1/images/edits`; declaring generations
does not grant edits, or vice versa. The authenticated key still owns routing,
including `auto` resolution. Only the model form field is replaced by that
resolved ID. Client form fields cannot override the destination or endpoint.
Copilot headers are reused, but Fetch supplies the multipart Content-Type and
matching boundary. The response is native JSON/error transport, without
protocol conversion, redirects, inference retries or account fallback.
Logs and stats use the existing `images` format and `copilot-images` strategy,
with the edits path distinguishing requests. Image bytes, form contents and
`b64_json` are not logged, including upstream error echoes. Accounting observes
only reported image usage.

Example (a live call consumes image credits; run only when authorized):

```sh
curl "$RAVEN_BASE_URL/v1/images/edits" \
  -H "Authorization: Bearer $RAVEN_API_KEY" \
  -F "model=gpt-image-2.5-flare" \
  -F "image[]=@source.png" \
  -F "prompt=Replace the background with a plain blue sky." \
  -F "quality=low" \
  -F "output_format=png"
```

OpenAI's [image guide](https://developers.openai.com/api/docs/guides/image-generation)
documents multipart edits with multiple images and masks. GitHub's
[2026-10-28 announcement](https://github.blog/changelog/2026-10-28-generate-and-edit-images-directly-in-copilot/)
confirms Flare generation and editing in Copilot. Together with the advertised
catalog path, this supports implementing a gated transport, but does not prove
Copilot's multipart contract, a particular account's entitlement or parameter
support. **No live Copilot edit was sent for this implementation**: tests use
synthetic uploads, isolated SQLite and mocked upstream HTTP. A separately
authorized successful multipart edit is still required for live acceptance.

## Routing and Credentials

The endpoint uses existing `/v1/*` API-key authentication, key-bound routing,
IP admission, rate limiting, quota settlement, request logging and cancellation.
Environment and database API keys work normally; internal management credentials
never authorize inference. A custom-only key does not gain access to Copilot.
`auto` resolves through the selected rule; explicit model IDs remain unchanged.

Only Copilot models declaring the exact `/v1/systemone` endpoint are eligible.
Catalog declarations are capability evidence, not entitlement checks. The
existing cached `/v1/models` aggregation remains unchanged and is not filtered
by the calling key's routing rule. Upstream permission failures are authoritative.

The Copilot token's validated HTTPS `endpoints.api` destination is captured
alongside that token during initialization and refresh. Systemone requires
this destination rather than guessing a personal-account host. Only Copilot
API hosts with no userinfo, custom port, path, query or fragment are accepted.
Client JSON cannot override the destination, credentials, or routing selection.

## Native Wire Behavior

- Accept a nonempty model, a `state` field and a nonempty named `questions`
  object; every question has a string `type`. Preserve unknown fields and
  structured values, including exact numeric lexemes through Bun's native
  source-preserving JSON support. Upstream owns detailed validation and limits.
- Forward the same native JSON structure to `/v1/systemone`. No Chat, Messages,
  Responses, `/v1/decisions`, model-name or probability conversion occurs.
- Preserve successful JSON response text without reserializing numbers or
  inserting missing `model`, `usage`, `confidence`, `legend` or distributions.
  This is transport support, not an exhaustive semantic schema validator.
- Systemone accounting observes only reported `usage.input_tokens` and
  `usage.output_tokens`. Chat-style `prompt_tokens`/`completion_tokens` aliases
  are not accepted for Systemone. Missing buckets stay null and incomplete usage
  remains incomplete.
  Cache buckets are not invented. Accounting never changes the wire body.
- Preserve upstream error status and bounded, credential-redacted body. Do not
  forward credentials, cookies, arbitrary upstream headers or redirect targets.
  Malformed successful JSON or an unexpected success content type returns 502.
- Recognized HTTP 200 error/refusal bodies receive the same redaction and
  length bound as non-2xx errors; truncation never changes their failure outcome.
- Preserve native error/refusal JSON; record recognized error/refusal bodies as
  errors even when upstream HTTP is 200. Never turn them into fabricated answers.
- Do not retry, refresh credentials on an inference failure, switch accounts,
  probe another path or follow a redirect. Client cancellation stops transport.
- Non-streaming-only is a Raven limit, not a verified Copilot SSE restriction.
  The existing text-ping diagnostic refuses decision models instead of sending
  a chat prompt. Do not synthesize SSE or a `[DONE]` marker.
